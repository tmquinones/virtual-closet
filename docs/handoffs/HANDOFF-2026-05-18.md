## What was done this session

### 1. Wear logging — full stack fix (v66)

**Problem:** Wear count didn't persist after refresh, no way to back-date a
wear, and logging an item in the Daily Log didn't update the wear count.

**Changes:**

- `server/src/migrations/004_wear_log.sql` (NEW) — adds `wear_log TEXT`
  column to `items` table. Requires a full container rebuild to apply (not
  just restart) since src/ is baked into the image at build time.

- `server/src/routes/items.js` — added `wear_log` to `JSON_FIELDS` array;
  added `wear_log=@wear_log` to both the INSERT and UPDATE handlers.

- `js/db-r4.js` — `_rowToItem` now maps `wear_log` → `wearLog` (array);
  `_itemToBody` now sends `wear_log` back to the API.

- `js/wear-r1.js` — complete rewrite. Now uses ISO date strings
  (`"YYYY-MM-DD"`) instead of Unix timestamps. `recordWear(itemId, dateStr)`
  accepts an optional past date. New back-date UI: "Log a wear" button reveals
  a date picker (max = today) with "Log it" / "Cancel". `_refreshWearStats()`
  updates the wear card without a full re-render.

- `js/daily-r1.js` — `saveDaily()` now diffs old vs new item IDs on save.
  Items added to a daily log entry get the log's date pushed into their
  `wearLog`; items removed get that date spliced out.

- **Backfill script** (`backfill-wear-log.js`, run once from workspace) —
  authenticated via API, read all 8 existing daily log entries, and stamped
  wear dates onto 21 items that had been logged before this feature existed.

### 4. Wishlist "Show Similar" — accuracy overhaul (v66–v70)

**Problem:** "Show Similar" was returning wildly inaccurate results — all
shoes matched all shoes, tank tops showed for zip-up jackets, shorts showed
for pants, etc.

**Root causes found and fixed across v66–v70:**

1. `garmentType` match alone (+5 pts) was enough to pass the threshold,
   so every shoe matched every shoe.
   → Lowered garmentType to +3 pts; threshold stays at 5, so garmentType
   alone (3) can no longer pass.

2. `passesSubtype` was a no-op when the wish item had no explicit subtype set
   — it returned `true` for everything.
   → Now infers subtype from item name when the field is blank.

3. `mkEffective` was reading `cand.subtype` (lowercase) but closet items store
   the field as `cand.subType` (capital T) — always reading `undefined`.
   → Fixed to check `cand.subType || cand.subtype` first.

4. Even with correct field reading, `"Jacket" !== "Zip-up"` — they scored 0
   against each other, so Full-Zip jackets in the closet never matched a
   Full-Zip wishlist item.
   → Added a **subtype family system** (`SUBTYPE_FAMILIES` map in
   `wishlist-r6.js`). Families: `zip-jacket` (Zip-up, Jacket, Blazer, Vest,
   Coat), `pants` (Pants, Jeans), `sandal` (Sandals, Slippers, Slides),
   `athletic-shoe` (Sneakers, Athletic), etc.
   Same-family match = +5 pts (same as an exact subtype match).
   Exact match = +6 pts.

5. Mixed color swatches like "White/Twilight Blue" didn't match "White".
   → Added primary color extraction (split on `/` or `,`, take first token)
   for color comparison.

6. Missing keywords for slippers, slides, earrings, necklace, bracelet,
   cami/camisole, full zip/zip-up, half-zip, tennis shoe, court shoe.
   → All added to `SUBTYPE_KEYWORDS`.

**Net result (v70 scoring):**
- garmentType alone (3 pts) → below threshold → blocked ✓
- garmentType + color family (3+2 = 5) → passes ✓
- garmentType + same subtype family (3+5 = 8) → passes ✓
- garmentType + exact subtype (3+6 = 9) → passes ✓
- Same subtype family across categories (0+5 = 5) → passes ✓
  (covers Full-Zip in "tops" wishlist matching Jacket in "outerwear" closet)
- Tank top vs Zip-up → different families → blocked by passesSubtype ✓
- Shorts vs Pants → different families → blocked ✓
